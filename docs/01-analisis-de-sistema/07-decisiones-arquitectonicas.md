# Decisiones arquitectónicas

| ID | Título | Drivers relacionados | Decisión arquitectónica | Justificación | Resultado |
|---|---|---|---|---|---|
| ADR-01 | Monolito modular inicial | DA06, DA07 | Utilizar un monolito modular como arquitectura principal del backend, manteniendo el servicio de Notificaciones como proceso independiente. | Reduce la complejidad inicial de desarrollo y despliegue, facilita la comunicación entre módulos y permite mantener consistencia en las operaciones principales. La separación de Notificaciones responde a la restricción académica RC09. | Usuarios, Farmacias, Medicamentos, Búsqueda, Inventario, Reservas y Administración estarán organizados como módulos internos de una API desarrollada con Node.js, Express y TypeScript. Notificaciones será un servicio separado. |
| ADR-02 | Organización por capas | DA06 | Organizar los módulos del backend en capas de presentación, aplicación, dominio e infraestructura. | La separación de responsabilidades facilita el mantenimiento, las pruebas y la evolución del sistema, evitando mezclar lógica de negocio con detalles técnicos. | Cada módulo tendrá responsabilidades diferenciadas para controladores, casos de uso, entidades, contratos, repositorios y adaptadores. |
| ADR-03 | Clean Architecture | DA05, DA06 | Aplicar Clean Architecture dentro de los módulos del monolito modular, utilizando dependencias dirigidas hacia las abstracciones internas. | Permite proteger las reglas de negocio frente a cambios en frameworks, mecanismos de persistencia o servicios externos. | El dominio no dependerá de Express, PostgreSQL, Redis ni proveedores externos. Las implementaciones técnicas estarán ubicadas en infraestructura y serán conectadas mediante composición e inyección de dependencias. |
| ADR-04 | PostgreSQL transaccional | DA01, DA02 | Utilizar PostgreSQL como base de datos principal y mecanismo de persistencia transaccional para las operaciones del sistema. | Las reservas, el inventario y sus relaciones requieren integridad de datos, restricciones y control de concurrencia. PostgreSQL permite coordinar operaciones críticas mediante transacciones. | PostgreSQL almacenará usuarios, farmacias, medicamentos, inventario, movimientos_inventario, reservas y eventos Outbox. El historial incluirá producto, farmacia, cantidad anterior y nueva, motivo, responsable y fecha. Las operaciones críticas utilizarán transacciones, restricciones de integridad y mecanismos de control de concurrencia. |
| ADR-05 | Puertos y adaptadores | DA05, DA06 | Utilizar contratos y adaptadores para acceder a infraestructura y servicios externos, incluyendo notificaciones, pagos, mapas, caché e inventario externo futuro. | Permite sustituir implementaciones tecnológicas sin modificar las reglas centrales del negocio y facilita realizar pruebas con adaptadores simulados. | Se definirán contratos para persistencia, inventario, notificaciones, pagos futuros, mapas y caché. Las implementaciones concretas se ubicarán en infraestructura. |
| ADR-06 | Seguridad por rol y recurso | DA04 | Aplicar autenticación y autorización considerando tanto el rol del usuario como su relación con el recurso solicitado. | Un cliente no debe acceder a reservas ajenas y el personal de una farmacia no debe administrar información de otra sin autorización. | Las búsquedas públicas podrán realizarse sin autenticación. Las reservas y operaciones administrativas requerirán autenticación y permisos por recurso. El dueño o administrador verificará físicamente el producto antes de aceptar PENDIENTE; el personal solo podrá aceptarla con delegación expresa. Cada farmacia gestionará su inventario; FarmaFind supervisará. |
| ADR-07 | Redis como caché obligatoria del MVP | DA01, DA03, DA07 | Incorporar Redis como contenedor de caché obligatorio del MVP para almacenar temporalmente resultados de búsqueda de medicamentos y farmacias. | Las búsquedas pueden generar consultas repetidas sobre medicamentos, farmacias y disponibilidad. Redis permite reducir accesos repetitivos a PostgreSQL y ofrece una alternativa de optimización que podrá evaluarse mediante pruebas de rendimiento. | Redis formará parte de los contenedores del MVP y será utilizado por el módulo Búsqueda. PostgreSQL continuará siendo la fuente oficial de datos y la única fuente utilizada para confirmar reservas e inventario. |
| ADR-08 | Estrategia Cache-Aside y control de vigencia | DA01, DA03, DA06 | Utilizar Cache-Aside mediante un puerto de caché y un adaptador Redis. Aplicar TTL configurable e invalidación de entradas cuando cambien datos relevantes. | Permite acelerar consultas sin convertir la caché en almacenamiento principal ni introducir dependencias directas con Redis en los casos de uso. El TTL y la invalidación limitan la exposición de resultados desactualizados. | El módulo Búsqueda consultará Redis antes de PostgreSQL. Ante un fallo de caché consultará PostgreSQL directamente. Se propone un TTL inicial configurable de 60 segundos para resultados con precios o disponibilidad, sujeto a validación. La invalidación se realizará después del commit, incluidas importaciones y ajustes. La búsqueda mostrará disponibilidad referencial y fecha de última revisión por la farmacia; TTL no acreditará existencia física. |
| ADR-09 | Consistencia transaccional entre Reservas e Inventario | DA01, DA02, DA04 | Ejecutar el compromiso de stock, el registro de la reserva y el registro del evento correspondiente dentro de una misma transacción PostgreSQL, utilizando una unidad de trabajo compartida. | La verificación y actualización independientes del stock pueden provocar condiciones de carrera y operaciones parcialmente persistidas. Una transacción compartida, acompañada de operaciones atómicas de inventario, permite mantener la consistencia. | El módulo Reservas coordinará con Inventario mediante contratos públicos y un contexto transaccional común. La operación completa se confirmará únicamente cuando todas sus acciones sean exitosas; en caso contrario se revertirá. Redis no participará en estas transacciones. Para el MVP, la importación será atómica por archivo: si una fila es inválida o no está conciliada, no se guardará ninguna; se presentará un reporte de errores para corregir y reintentar. Los ajustes e importaciones revalidarán compromisos concurrentes, conservarán movimientos_inventario y no guardarán stock físico inferior al comprometido; las discrepancias exigirán conciliación. |
| ADR-10 | Ciclo de vida único de reservas | DA02, DA04, DA06 | Establecer los estados PENDIENTE, CONFIRMADA, ENTREGADA, CANCELADA y EXPIRADA, con transiciones explícitas y validaciones de autorización y vigencia. | Un modelo único evita contradicciones entre requisitos, diagramas, casos de uso y futuras implementaciones. También permite controlar correctamente la liberación o consumo definitivo del stock. | PENDIENTE podrá pasar a CONFIRMADA, CANCELADA o EXPIRADA. CONFIRMADA podrá pasar a ENTREGADA, CANCELADA o EXPIRADA. ENTREGADA, CANCELADA y EXPIRADA serán estados terminales. PENDIENTE tendrá un plazo de respuesta configurable de 20 minutos iniciales. Al aceptar tras comprobar existencias físicas, se asignará a CONFIRMADA un plazo de recogida configurable de 24 horas inicialmente propuestas, sujeto a validación. Ante falta física se cancelará PENDIENTE con motivo STOCK_FISICO_INSUFICIENTE, incidencia y alerta de corrección. Cancelación y expiración liberarán compromisos una sola vez; la entrega descontará stock físico y comprometido. |
| ADR-11 | Transactional Outbox para integración con Notificaciones | DA05, DA08, DA09 | Registrar los eventos relacionados con reservas, alertas de corrección y recordatorios propuestos de inventario antiguo en una tabla Outbox de PostgreSQL, dentro de la misma transacción del proceso de negocio. Publicarlos posteriormente hacia el servicio independiente de Notificaciones mediante HTTPS/REST autenticado. | El envío directo de notificaciones durante la creación de reservas podría provocar fallos aparentes o pérdida de eventos cuando el servicio externo no esté disponible. Transactional Outbox permite conservar los eventos pendientes y procesarlos posteriormente. | Un publicador del núcleo procesará los eventos Outbox y aplicará reintentos. El servicio de Notificaciones identificará los eventos mediante identificadores únicos para evitar trabajos duplicados. La creación de reservas no dependerá de la disponibilidad inmediata del servicio. La detección de inventario antiguo registrará el recordatorio en Outbox con umbral y frecuencia configurables, sin alterar existencias. |
| ADR-12 | Delimitación del MVP y extensiones futuras | DA05, DA06, DA09 | Establecer como parte del MVP la búsqueda de medicamentos, gestión de farmacias, inventario, reservas, administración, Redis y Notificaciones. Mantener el pago electrónico y la integración con inventarios externos como funcionalidades futuras. | Permite definir un alcance académico viable sin introducir dependencias que no son necesarias para demostrar los procesos centrales del sistema. | El MVP permitirá buscar y reservar medicamentos sin pago electrónico obligatorio. El inventario tendrá registro manual e importación obligatoria de Excel (.xlsx/.csv), con plantilla de nombre, concentración, presentación, precio referencial y stock físico, vista previa, validación y mapeo antes de confirmar; los productos se asociarán al catálogo general para evitar duplicidades. La estructura real de archivos deberá validarse con las farmacias. La sincronización automática por API REST/adaptadores quedará fuera del MVP. |
