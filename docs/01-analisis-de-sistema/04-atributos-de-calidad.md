# Atributos de calidad del sistema FarmaFind

| ID | Atributo | Escenario y medida propuesta |
|---|---|---|
| AC01 | Rendimiento | Bajo una carga de prueba definida y un conjunto de datos representativo, el percentil 95 (p95) de las búsquedas de medicamentos y farmacias deberá ser ≤ 2 segundos, con errores técnicos menores al 1 %. Redis será obligatorio en el MVP mediante la estrategia Cache-Aside. Se medirán p95, p99, throughput, consultas a PostgreSQL, porcentaje de aciertos y fallos de caché (hit rate y miss rate), latencia de Redis y consumo de recursos. Se comparará el rendimiento con caché habilitada y deshabilitada, utilizando la misma carga y conjunto de datos. Los conflictos de stock se registrarán separadamente de los errores técnicos. |
| AC02 | Disponibilidad | Con dos instancias del núcleo FarmaFind en ejecución, detener una y verificar que el servicio continúe atendiendo solicitudes mediante la instancia sana en ≤ 30 segundos. Adicionalmente, interrumpir Redis y comprobar que las búsquedas continúan utilizando PostgreSQL como mecanismo alternativo. La falla de Redis podrá reducir el rendimiento, pero no deberá impedir las búsquedas ni afectar las reservas. PostgreSQL seguirá siendo un punto único de fallo declarado durante el MVP. |
| AC03 | Escalabilidad | Comparar el comportamiento del sistema con una y dos instancias de la API FarmaFind, utilizando el mismo conjunto de datos y recursos equivalentes de PostgreSQL y Redis. Incrementar progresivamente la carga de búsquedas y reservas y medir la capacidad antes de superar el límite definido en AC01. Registrar throughput, p95, p99, consumo de CPU y memoria, conexiones a PostgreSQL y Redis, hit rate y miss rate. Documentar los cuellos de botella y determinar si Redis reduce la carga de consultas repetitivas sobre PostgreSQL. No se asumirá una mejora de escalabilidad sin evidencia obtenida durante las pruebas. |
| AC04 | Seguridad | El 100 % de los intentos de acceso no autorizado a reservas ajenas o de administración de otra farmacia deberán ser rechazados durante las pruebas definidas. Las operaciones protegidas requerirán autenticación y autorización por rol y recurso. Redis deberá estar restringido a los componentes autorizados del backend, con autenticación y configuración segura de red. No se almacenarán contraseñas, tokens de autenticación ni datos privados innecesarios en la caché de búsquedas. Los registros técnicos no deberán exponer contraseñas, tokens ni credenciales de PostgreSQL, Redis o servicios externos. |
| AC05 | Consistencia | Con 10 unidades disponibles de un medicamento y 100 solicitudes concurrentes válidas e independientes, cada una solicitando una unidad, deberán confirmarse exactamente 10 reservas distintas, sin stock negativo ni sobreasignación. La creación de la reserva, el compromiso del stock y el registro del evento Outbox deberán realizarse dentro de una única transacción PostgreSQL mediante Unit of Work. Las cancelaciones y expiraciones deberán liberar el stock comprometido una sola vez, mientras que las entregas deberán registrar su salida definitiva. Redis no participará en las transacciones ni se utilizará para confirmar disponibilidad. Los resultados de búsqueda almacenados en caché tendrán carácter referencial. |
| AC06 | Mantenibilidad | Deberá ser posible sustituir el adaptador Redis del módulo Búsqueda por una implementación simulada o por una implementación sin caché, sin modificar las entidades del dominio ni los contratos de los casos de uso. De manera equivalente, el adaptador de Notificaciones deberá poder sustituirse por uno simulado sin modificar las reglas de reserva. La validación consistirá en ejecutar las pruebas correspondientes y comprobar que los cambios se limitan a infraestructura y composición de dependencias. |
| AC07 | Interoperabilidad | Validar los contratos de integración entre la API FarmaFind, Redis y el servicio independiente de Notificaciones. El acceso a Redis deberá realizarse mediante un puerto y un adaptador, con operaciones de consulta, almacenamiento temporal e invalidación. Los eventos enviados a Notificaciones deberán seguir un contrato definido y contener un identificador único. Al repetir un evento con el mismo identificador, el consumidor deberá registrar un único trabajo lógico. La comunicación entre el publicador Outbox y Notificaciones utilizará HTTPS/REST interno autenticado. |
| AC08 | Resiliencia | Al interrumpir el servicio de Notificaciones durante 5 minutos, las reservas deberán continuar y los eventos pendientes permanecerán registrados en PostgreSQL mediante Transactional Outbox. Una vez recuperado el servicio, deberán procesarse los trabajos pendientes sin pérdida de eventos confirmados y registrarse el retraso de recuperación. Adicionalmente, al interrumpir Redis durante una prueba controlada, el módulo Búsqueda deberá continuar consultando PostgreSQL. El sistema deberá registrar los fallos de caché y restablecer su utilización cuando Redis vuelva a estar disponible. Las entradas de Redis tendrán TTL configurable, inicialmente propuesto en 60 segundos para resultados con disponibilidad o precios, y se aplicarán mecanismos de invalidación posterior al commit ante cambios relevantes. |
| AC09 | Observabilidad y pruebas | Cada reserva de prueba deberá poder relacionarse con registros y un identificador de correlación. Se medirán latencia de búsquedas, errores técnicos, conflictos de stock, throughput, CPU, memoria, conexiones de PostgreSQL, transacciones fallidas y eventos pendientes de Outbox. Para Redis se registrarán hit rate, miss rate, latencia, uso de memoria, errores de conexión, operaciones de invalidación y utilización del mecanismo alternativo de consultas a PostgreSQL. Se realizarán pruebas de rendimiento con y sin caché, concurrencia de reservas, interrupción de Redis, recuperación de Notificaciones y sustitución de adaptadores. Los resultados deberán relacionarse con los criterios de aceptación y escenarios de calidad correspondientes. |
